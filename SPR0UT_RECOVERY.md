# Sprout Recovery Document

**Purpose:** a detailed, narrative reconstruction of how this project got to its current state — not just what exists, but what was tried, what broke, how it was diagnosed, and what's still open. Written from *this conversation's* first-hand memory, cross-checked against the actual files on disk as of this writing.

**Important scope note before anything else:** this project has been worked on by **multiple parallel Claude Code sessions**, not just this one. Everything in Sections 1-12 below that describes *reasoning, debugging, or testing* is this conversation's own first-hand account — I lived through it. But when I went to verify the current files against my memory (twice — once for `CLAUDE.md`, again just now for this document), I found a large amount of additional work that a **different session** did in parallel, which I only know about by reading the resulting files, not by having built or debugged it myself. That work is called out explicitly wherever it appears, so nobody mistakes "verified by reading the file" for "verified by testing it end-to-end," which are very different confidence levels.

---

## 1. Original Sprout project goal

Relayed by the user as a full vision document partway through this conversation (after a large chunk of implementation had already happened). Core points:

- A pixel-art creature that lives as a real overlay on the Windows desktop — not inside a normal app window. Cream/beige body, dark outline, blush, stem + two leaves, and this design must **never** vary frame-to-frame.
- Natural idle life: stand, blink, look around, walk, turn around, sit, stand, occasionally wave/jump/dance — explicitly **not** constantly busy. "Sometimes it should just stand there peacefully."
- Transparent background — no scenery, grass, flowers, or ground objects in any sprite. Only Sprout, and the laptop prop when relevant.
- Emotions communicated visually: happy, excited, sad, angry/annoyed, confused, tired, giggly, proud.
- The laptop is a **temporary** prop, not part of Sprout's permanent design — appears only when Sprout sits down for a productivity task (checking a to-do list, etc.), then disappears.
- Reminders should feel conversational — a speech bubble with Yes/Done/Remind-later options, Sprout reacting emotionally to the answer, getting mildly annoyed after repeated snoozing.
- A lightweight local to-do list, no external APIs for v1.
- Click/interaction reactions: happy, wave, giggle, confused, jump, etc.
- Explicit build order: (1) core motion (idle/blink/walk/sit/stand/jump) feeling natural, (2) personality emotions, (3) laptop/productivity sequence, (4) reminders/to-do, (5) later — calendar/email/AI integrations, explicitly out of scope for v1.
- "The feeling I want": not "I installed another productivity app," but "there's this tiny creature living on my desktop that happens to care whether I'm getting things done."

Notably, the very first request in this conversation (before the vision doc was shared) was much shorter: *"can we make this has moving on my desktop and i can turn it off when needed."* I had to ask a clarifying question — real OS-level desktop overlay vs. an in-page browser animation — before any of the above context existed. The full vision doc came later and retroactively explained *why* the answer was "real overlay."

## 2. The complete plan(s) we developed

Three separate planning passes happened, in this order:

**Plan A — `rippling-drifting-lightning.md`** (this session, very first request). Covered: converting the bare React+Vite scaffold into an Electron desktop overlay (transparent/frameless/always-on-top/click-through window via `vite-plugin-electron`), a system tray with show/hide/quit, sprite-frame cycling + walking movement, a to-do list, a 2-hour water/walk reminder, a simple mood engine (task-count + interaction driven), and a standalone `electron-builder` installer. This was refined twice more via follow-up questions before approval — once to scope the to-do/reminder/mood/packaging asks precisely, once to tone down the visual style (drop a sparkle-burst click effect the user found too flashy). **Fully implemented** — see Section 3.

**Plan B — `tender-popping-peacock.md`, my version** (this session, after the vision doc). Scoped to just "Phase 1" of the vision doc's own build order: give Sprout natural idle-behavior variety (occasional blink/jump/sit-rest, not just idle↔walk) using art that already existed but was unused. Reused the existing `useWalk` pause mechanism (originally built for the to-do panel) to freeze walking during a micro-behavior. **Fully implemented** — see Section 3.

**Plan B, refined** — after approval, the user sent three specific refinements (see Section 4 for exactly how that message arrived): keep blink idle-only for now but architect it as an independent hook (not baked into the jump/sit scheduler) so it can later run during other states; retune the probabilities calmer (~30% blink / 7% jump / 6% sit / 57% nothing) and randomize the check interval (3-7s) instead of a fixed cadence; suppress jump/sit during moods/interactions but keep blink separately toggleable for that later. **Implemented** — see Section 3.

**Plan C — `tender-popping-peacock.md`, overwritten by a different session.** At some point after I wrote Plan B to that file, **a different Claude Code session reused the same filename** and replaced its contents entirely with a much bigger plan: "Sprout: Central Emotion/Reaction Architecture (Phases 1-3)" — a proper priority-based reaction controller (`useReactionController.js`, layers: interaction > reaction > work > emotion > microBehavior > locomotion), a true non-destructive blink overlay (`useBlinkOverlay.js`), and corrected to-do/laptop sequencing (trigger on panel-open + first-keystroke, not input focus/blur). **I did not write this plan and was not present for its approval.** I only know its contents by reading the file. Critically: **the two new hook files it describes exist on disk, but neither is wired into `Sprout.jsx`.** The plan appears to have been designed but not (yet) executed against the actual component. See Section 12 for the exact current mismatch.

## 3. Every major implementation step this session completed

In the order they happened:

1. **Step 0 — Fixed broken animation plumbing.** The original scaffold had `src/hooks/useAnimation.js` importing `../utils/animations`, but the actual file on disk was `src/utils/animation.sjs` (wrong extension, wrong pluralization) — a dead import that would have crashed any real usage. Renamed/rewrote it as `src/utils/animations.js`, and added `src/utils/spriteFrames.js` using `import.meta.glob("../assets/sprites/**/*.png", { eager: true })` to build a frame lookup generically by folder name — no per-sprite hardcoding, frame count derived at runtime. Verified with `npm run build`.
2. **Step 1 — Electron scaffold.** Installed `electron` + `vite-plugin-electron`. Wrote `electron/main.js` (window creation) and `electron/preload.cjs` (contextBridge). **This failed on the first attempt** — see Section 8, Bug #1, for the full diagnosis (wrong plugin API version).
3. **Step 2/3 — Window + tray.** Transparent/frameless/always-on-top/skipTaskbar `BrowserWindow`, sized to the primary display's work area; default click-through via `setIgnoreMouseEvents(true, { forward: true })`, toggled off on hover via IPC; `Tray` built from a resized `hero.png` with Show/Hide/Quit menu items.
4. **Step 4 — Sprite-frame cycling + walking.** New `useSpriteFrame.js` (frame-index cycling driven by `animations.js` config + `spriteFrames.js` lookup) and `useWalk.js` (a `requestAnimationFrame`-driven idle↔walk phase state machine with randomized 3-8s idle / 2.5-6s walk phases, bounded to the screen width). Rewired `Sprout.jsx` to use real sprite frames + horizontal movement instead of a single static idle image. **Caught and fixed a geometry bug during this step** — see Section 8, Bug #2.
5. **Step 4.5 — Toned down the visual style.** Removed a CSS sparkle-burst effect and reduced a bounce-animation's amplitude, per explicit user feedback that the original design felt "too dashy and sparkling."
6. **Step 5 — CSS transparency + layout.** Made `html`/`body`/`#root`/`.app` backgrounds transparent (replacing a solid gradient), restructured the character container into `.sprout-rig` (position) + `.sprout-flip` (direction-flip, kept separate from the position transform specifically to avoid CSS-keyframe-vs-inline-style conflicts on the same element).
7. **Step 6 — To-do list.** `useTodos.js` (localStorage CRUD) + `TodoPanel.jsx` (add/toggle/edit/delete, inline double-click-to-edit) + `Todo.css`, wired into `Sprout.jsx` via a 📋 toggle button.
8. **Step 7 — 2-hour water/walk reminder.** Main-process `setInterval` + native `Notification` + IPC channel to show the same message in Sprout's speech bubble, plus a consecutive-ignored-reminders counter (feeds the mood engine). Smoke-tested with a temporarily shortened interval — see Section 10.
9. **Step 8 — Mood engine.** `src/utils/mood.js`: a pure `computeMood()` function (task-count and ignored-reminder thresholds → `tired`/`angry`) plus `createRapidClickTracker()` for a rapid-click → `confused` easter egg. Designed from the start to degrade gracefully (fall back to idle art) when the corresponding emotion sprite folder is empty, since no emotion art existed yet at this point.
10. **Step 9 — Standalone packaging.** Installed `electron-builder`, added a `build` config to `package.json` (NSIS target, output to `release/`), added an `npm run dist` script. Produced `release/Sprout Setup 0.0.0.exe`. Verified by running the **unpacked** build directly (`release/win-unpacked/Sprout.exe`) rather than the installer — deliberately avoided running the actual installer myself since installing software modifies the user's system (Start Menu shortcuts, registry), which felt like the user's call to make, not mine.
11. **Demo GIF generation.** Built a short animated GIF of Sprout on the real desktop, entirely with tools already on the system (PowerShell + WPF's `GifBitmapEncoder` — no `ffmpeg`, no new installs). Full story in Section 10.
12. **Phase 1 idle-behavior variety** (Plan B above): `useIdleScheduler.js` (new), fixes to `spriteFrames.js` and `animations.js`, a substantial rewrite of `Sprout.jsx`'s phase/behavior state. Then, per the refinement message, **split blink out into its own `useBlinkScheduler.js`**, independent of the jump/sit scheduler, and retuned the probabilities/interval.

## 7. Important code/architecture decisions

- **Sprite loading is fully generic.** `spriteFrames.js` globs and groups by folder name + numeric suffix. Adding/removing/renumbering frames in an existing folder needs zero code changes — this was a deliberate choice from Step 0 onward, specifically so future art additions (which did happen, repeatedly, from the other session) wouldn't require touching the loader.
- **`RIG_OFFSET` geometry fix** (Section 8, Bug #2) — the walk-bounds math is deliberately expressed in the character's own screen-space coordinates, with the wider rig container's offset subtracted at render time, rather than baking the offset into the bounds calculation itself. Keeps `useWalk.js` ignorant of the rig's internal layout.
- **`useWalk`'s `paused` flag** was built for one purpose (freeze movement while the to-do panel is open, so the input box doesn't slide out from under a mid-typing user) and then **deliberately reused** for a second purpose (freeze movement during idle micro-behaviors like sit-rest, so Sprout doesn't wander off mid-sit) rather than building a second mechanism. Same pattern, two callers.
- **Blink built as its own independent scheduler**, not folded into the jump/sit idle scheduler — an explicit architectural requirement from the user's refinement message, anticipating that blink will eventually need to run during states (walking, sitting, working) that jump/sit never will.
- **Mood degrades gracefully when art is missing.** `useSpriteFrame` falls back to the idle frame array whenever `spriteFrames[currentAnimation]` is empty — this was load-bearing for most of the session, since `angry`/`confused`/`tired`/`happy`(dedicated)/`sad`/`giggly` art didn't exist yet when the mood engine and click-reaction system were first built. Nothing had to be rewritten when the art arrived later; it just started rendering.
- **Chose not to run the installer myself.** Verified the standalone build by launching the unpacked `.exe` directly instead. A deliberate boundary: producing the installer is a build step, running it is a system-modifying action.
- **Screenshot-based verification was deliberately scaled back over the session** — starting from full-screen captures, narrowing to small cropped regions, and eventually stopped entirely once they revealed personal content on the user's screen. See Section 9.

## 8. Errors and mistakes encountered, and how they were diagnosed/fixed

**Bug #1 — Electron main process failed to load (`SyntaxError: Cannot use import statement outside a module`).**
First `npm run dev` after the Electron scaffold crashed. Root cause: I initially configured `vite.config.js` using the *old* `vite-plugin-electron` array/flat API (`entry` + `vite.build.rollupOptions.output`), but the version actually installed (`1.1.1`) targets Vite 8, which renamed the relevant bundler option key from `rollupOptions` to `rolldownOptions` — my override silently did nothing, so the output stayed ESM while I'd also forced the file extension to `.cjs`, and Node refused to parse ESM syntax inside a `.cjs`-named file. **Diagnosis method:** read the actual installed package's `README.md` directly (`node_modules/vite-plugin-electron/README.md`) rather than assuming the API from memory — it documented the current `vite-plugin-electron/simple` API with a `{ main: { entry }, preload: { input } }` shape. Rewrote `vite.config.js` accordingly, and updated `package.json`'s `main` field from the wrong `dist-electron/main.cjs` to the correct `dist-electron/main.js`. Rebuilt clean, verified via process/window-title check.

**Bug #2 — Character could walk partway off the right edge of the screen.**
While wiring up movement, I noticed the walk-bounds math (`useWalk.js`) used `CHARACTER_WIDTH = 190` for its bounds, but the actual positioning container (`.sprout-rig`) was 320px wide with the character centered inside via a 65px offset. At the computed max-x, the character's true screen position would have been ~65px further right than the intended bound — visually walking off-screen. **Caught before it ever shipped**, during code review while wiring the render, not via live testing. Fixed by introducing a `RIG_OFFSET` constant in `Sprout.jsx` and shifting the rig's `translateX` by that amount, so `useWalk`'s `x` value directly represents the character's own screen-space left edge (matching what its bounds math assumes), rather than the rig's.

**Bug #3 — Could not programmatically click-test the to-do toggle button.**
Wanted to verify the 📋 button actually opened the to-do panel. Two approaches failed:
1. Screenshot the button's position, then simulate an OS click there via `user32.dll` — missed twice, because Sprout had walked to a new position in the several-second gap between taking the screenshot and executing the click (each attempt is a separate tool round-trip with real latency). Notably, the *miss itself* was informative: the stale click passed transparently through to whatever window was behind Sprout at that point, which is a positive confirmation that click-through was working correctly — it just didn't prove the button was clickable.
2. Switched to Windows UI Automation (`FindFirst` by accessible name "Open to-do list") to locate the element programmatically instead of guessing coordinates — returned "BUTTON NOT FOUND." **Diagnosis:** Electron/Chromium doesn't build its full accessibility tree by default (a performance optimization) unless something explicitly requests it (a screen reader, or `app.setAccessibilitySupportEnabled(true)`), so UI Automation had nothing to see into the renderer's DOM.
**Resolution:** gave up on automated interaction-testing for this specific case and told the user directly that this one thing needed their own manual click-test, rather than either claiming false verification or spending unbounded effort automating around a tooling gap.

**Bug #4 — "Why isn't Sprout popping up?" (the biggest one).**
The user reported Sprout wasn't appearing after trying to run it. Diagnosis:
- `tasklist` showed only 3 `electron.exe` processes running, and `Get-Process electron | Select MainWindowTitle` showed **no window title at all** on any of them — the healthy signature is 4 processes with one titled `sprout-desktop`. This meant a process tree had started (main process) but the actual renderer/content process never spawned — the window never really came up.
- Investigated with `Get-CimInstance Win32_Process` to get full command lines for every `node.exe`/`electron.exe` on the machine — this surfaced that the user has **other, unrelated projects and tools running on the same machine** (a separate "Task Manager" app with its own Vite dev server on port 5174, `chrome-devtools-mcp` instances, Playwright driver processes). Important to distinguish these from Sprout's own tree before touching anything.
- Identified Sprout's specific broken tree (vite on port 5173 → a 3-process electron tree with no renderer) and killed **only that tree**, by PID, with `taskkill //F //PID <id> //T` — not a blanket `taskkill //IM electron.exe` or `//IM node.exe`, which would have collaterally killed the user's other unrelated work.
- **Root cause:** leftover Electron/Vite processes from my own earlier testing sessions were never fully cleaned up — I had been consistently killing `electron.exe` after each test, but never the underlying `node.exe`/vite parent process each `npm run dev` spawns. When a new instance launched while an old one's vite server was still holding port 5173 (or in some half-alive state), the new instance's window silently failed to render.
- **Fix:** killed the stale tree, confirmed port 5173 was free, relaunched clean — got the healthy 4-process signature immediately, and visually confirmed via a cropped screenshot that Sprout was genuinely rendering (just positioned at the screen's right edge at that moment, which is why it might have been easy to miss at a glance — not a bug, just where its random walk had taken it).
- **Told the user directly:** never run `npm run dev` a second time while one is already running; check for/close an existing terminal first.

**Bug #5 — `happy`/`confused` reactions could get permanently stuck.**
Found while investigating an unrelated oddity in a generated demo GIF (see Section 10). `useSpriteFrame`'s completion-callback logic only fired for a non-looping animation once `frameIndex` reached `frameCount - 1` — but that branch was gated behind `frameCount > 1`. At the time, `happy` and `confused` had no dedicated art and fell back to the single-frame idle image, so `frameCount` was `1` and the completion callback would **never fire** — meaning once triggered, Sprout could get stuck in the happy/confused reaction forever, with no path back to idle/walk. **Fixed** by adding a `setTimeout`-based fallback: any non-looping animation with only one available frame still auto-completes after its configured `frameDuration`, regardless of frame-index progression. Verified via `npm run build`; this fix predates the later arrival of real dedicated `happy`/`confused` art, so it may now be dead-code-safe rather than load-bearing, but it's still correct defensive behavior for any future one-shot animation that temporarily lacks art.

## 9. How we tested Sprout, and what happened

Testing was almost entirely manual/live rather than automated (no test suite exists in this project) — `npm run build` for fast compile-correctness, then `npm run dev` plus one or more of: process/window-title checks, screenshots, or (rarely, and with mixed success — see Bug #3) simulated interaction.

Notable outcomes:
- **First transparency test** (right after the Electron scaffold started working): a full-screen screenshot showed Sprout genuinely composited over the real desktop — visible through it were the Claude Code app's own "still working" dialog and desktop icons, plus incidentally a document in the background titled "Color grading reference for animation" listing mood designs (Tired, Sleepy, Surprised, Love, Proud). Flagged this to the user rather than acting on it, since it looked like it might be from a separate conversation of theirs about the same project.
- **Reminder smoke test:** temporarily shortened the reminder interval to 8 seconds, launched, waited, and confirmed the speech bubble displayed the real reminder message ("🚶 Stretch your legs") — solid end-to-end proof the main-process timer → IPC → renderer pipeline worked. Could **not** confirm the native Windows toast notification specifically fired (a known limitation of unpackaged dev-mode Electron apps on Windows, which often need a proper installed shortcut/AppUserModelID for toasts to behave reliably) — stated this as an open item rather than claiming full success. Reverted the interval to the real 2 hours immediately after.
- **Demo GIF capture revealed something unexpected.** After assembling a short GIF of Sprout via a PowerShell/WPF script, the very first frame showed Sprout displaying the "confused" reaction message — which nothing in my own script had triggered. Investigating with a fresh screenshot showed the desktop now displaying a completely different browser tab with no Sprout visible at all. Concluded the most likely explanation was that the **user themselves** had been actively using their computer during the capture window — clicking Sprout a few times (triggering the real rapid-click "confused" easter egg) and then switching apps. Treated as benign — arguably a nice confirmation the click reaction works for real — rather than a bug, though it's exactly what led to finding Bug #5 above while reasoning through it.
- **Privacy boundary reached and respected.** A later screenshot taken to confirm Sprout was still animating (during the Bug #4 investigation) incidentally showed the user's WhatsApp Web window with visible private chat/contact content. At that point I explicitly told the user I'd stop taking further full-screen screenshots, and switched to either process-level checks (no screen content involved) or small cropped regions for the remainder of the session. This is a real limitation on how thoroughly this session could visually verify later changes — later verification passes (e.g. confirming the idle-behavior scheduler and blink-scheduler split) relied more on process-health checks and a single small cropped screenshot than on extended visual observation, by design.
- **Packaging test:** ran the unpacked standalone build (`release/win-unpacked/Sprout.exe`) directly — confirmed via process check and a screenshot that it launches and renders identically to the dev build, with zero terminal/npm dependency, before ever running the actual installer (which was deliberately left for the user to run themselves).

## 14. Decisions/preferences that should not be changed

- **"Smallest safe changes"** — explicitly stated preference for incremental, narrowly-scoped work over large simultaneous rewrites.
- **Mood does not suppress walking** — confirmed explicitly: an active `tired`/`angry`/`sad` mood only shows during idle moments between walk bouts; walking continues regardless.
- **No fixed-cadence timers for autonomous behavior** — both the idle (jump/sit) and blink schedulers deliberately use a self-rescheduling randomized 3-7s gap, per an explicit correction (they originally used a fixed interval).
- **Character-art lock** — never rename/resize/recolor/"fix" existing sprite PNGs without being asked, including the misnamed `gigglish` folder and a known crosshair-cursor artifact left in one draft `angry` frame at the user's explicit choice.
- **Standalone packaging stays in scope**, not deferred — the user explicitly wants to run Sprout without keeping a terminal/editor open.
- **Never run `npm run dev` a second time while one is already running** — this caused the biggest bug of the session (Bug #4). Always check for/kill stray Sprout-specific `electron.exe`/vite processes before relaunching — never a blanket kill of all `node.exe`/`electron.exe` on the machine, since the user runs other unrelated projects on the same machine.
- **Don't run the installer, or take other system-modifying actions, unilaterally** — verify standalone builds via the unpacked `.exe` instead, and let the user choose when to actually install.
- **Full-screen screenshots should be avoided** — this session deliberately stopped using them after they twice revealed unrelated personal content (another AI chat's visible notes, then WhatsApp messages). Prefer process-level health checks or small cropped regions when visual verification is genuinely needed, and say plainly when something can't be verified this way rather than over-capturing to compensate.
- **Don't wire in `useReactionController.js`/`useBlinkOverlay.js` unilaterally** — this is a real architectural rewrite belonging to a plan this session didn't originate; per the cross-session decision point in Section 13, confirm with the user first.
